日期：2026-11-25（v2 按 Codex 独立评审修订）。范围：用户提出的第三维度——「后续升级发版会不会丢数据」，
以及采集端→服务端整条链路的健壮性、鲁棒性、幂等性。配套：
`2026-11-25-client-server-throttle-audit.md`（交互与节流）、`2026-11-25-d1-read-optimization-research.md`（D1 读写）。
本文是评估，不含代码改动。标注：**已验证** = 读代码/跑命令得到；**推断** = 结构外推；**未覆盖** 显式标出。

v2 相对 v1 的关键修正：结论从「升级本身不会丢数据」收窄为**有条件成立**——
二进制自更新的恢复链成立，但 skill 目录交换与「无持久游标的来源靠 since 窗口重读」两处会让「最坏只漏一轮」
不成立；另新增 v1 漏掉的风险（§5.4–5.6 为数据风险 G10/G11/G12；§5.7 为文档缺口）。

## 零、结论摘要

**二进制客户端（clientType=binary）的升级链是稳的**：先完整性校验 → 探针 → 备份 → 两跳 rename →
启动前恢复；状态与代码物理分离；重传由服务端 hash 幂等吸收。这一条在 v2 复核后仍然成立。

**但「全链路、无条件不丢数据」不成立**，v1 的表述过宽。按严重度：

| #   | 缺口                                                                                       | 级别 | 性质                      |
| --- | ------------------------------------------------------------------------------------------ | ---- | ------------------------- |
| G1  | 非日期类 400 让整批失败并计入 24h 暂停环；错误不可诊断；**同 stateDir 的多来源共享该暂停** | P1   | 错误处理/可诊断性         |

## 一、数据地形：分来源的投递保证（v2 修正）

v1 把所有来源都描述成「持久化 at-least-once」，这不准确。**投递保证按来源分两类**（已验证）：

| 类别         | 来源                                                                     | 未上传数据的持久化载体                                                                         | 断网/停机后的重试保证                                                                                |
| ------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| hook 游标类  | `claude-code`、`codex`                                                   | cursor 的 `pendingUpload` 条目（会话文件 + 快照组），永久保留直到 ack                          | 强：pending 不回收，恢复后逐组重试                                                                   |
| since 窗口类 | `pi`、`grok-build`、`deepseek-harness`、`opencode`、12 个 ccusage 工具源 | **无**；每次运行按 `since` 重扫本地存储                                                        | **有界**：默认回看 7 天（`sync-options.mjs` 的 `DEFAULT_LOOKBACK_DAYS=7`），超窗口的日期不会再被扫到 |
| 混合         | 三个 Antigravity 来源                                                    | 已采集游标里的 pending 组（可轮转重试 `since` 之外的组，`antigravitycli/provider.go:116,175`） | **部分强**：已采集部分不丢；从未采集的仍受源存储与扫描窗口限制                                       |

- 后果（已验证；Codex 终审补正分类后仍成立）：一台机器停机 9 天后恢复，默认 `since` = 今天−7，原来的第 1–2 天的数据即使源文件仍在，
  也会被 `pi.go:75-77` 一类的日期过滤跳过——**永久漏计**。Codex 探针复现了 `since` 从 20261125 跳到 20261127 后旧数据被排除。
- 7 天之内：每次成功收集都会覆盖窗口内全部日期，重传由 hash 幂等吸收，所以**窗口内完全自愈**。
- 修复方向（建议，P1）：把「最近一次成功同步的日期水位」持久化在状态目录，`since = max(默认回看, 水位−1天)`，
  让恢复后的第一次运行覆盖中断期。这比「持久化待传队列」简单得多，也不改变协议。
  注意上限：水位过旧（如 90 天）会放大扫描成本，需设一个上限（如 30 天）并显式告警。

其他数据的地形不变：定价缓存可重算；设备身份/上传 token 半权威（升级不触碰，重配对才变）；
服务端聚合是派生值，靠重传修复。

## 二、四条升级链路逐一核对

### 2.1 二进制 self-update（Go `internal/selfupdate`）——已验证成立

1. 发布解析走 `/releases/latest`，不用限流 REST API；重定向逐跳校验 host 且禁 https→http 降级。
2. 下载有 128 MiB 上界（边读边判）与超时；校验是 **SHA-256 完整性校验**（不是签名，见 G6）。
3. **无 checksums.txt 的 release 直接拒装**。
4. 新二进制先写 `<target>.new`，**先跑 `version` 探针**（10s 超时），通过才交换。
5. 交换 = `current→backup` + `staged→current`；第二跳失败主动回滚；回滚再失败会同时报告两个错误和 backup 路径。
6. 每次启动前 `recoverUnderInstallLock` 在 `self-update.lock` 下恢复缺失目标，不覆盖完好安装；hook 路径共用该锁。
   边界：hook 恰在「目标缺失 + 更新进行中」时本轮仍会失败（锁被占，恢复让路），但下一轮恢复。
7. 降级守卫：feed latest 低于已装版本拒装（pinned 除外）。
8. 升级在采集之前；hook 运行从不升级；升级失败只 warn。

**结论**：二进制路径「最坏只漏一轮」成立（前提是进程不是永久崩溃循环）。

### 2.2 skill 目录与 git checkout 升级——**v1 漏掉的窗口（G8）**

- 已验证的顺序（`upgrade-utils.mjs:128-160` 的 `replaceDirectory`）：
  `skillDir → skillBackupDir` 与 `staging → skillDir` 是两次独立的移动（rename，EXDEV 时退化为 copy+remove），中间被杀会留下**缺失或残缺的 skill 目录**；
  它没有等价于 `recoverOrphanedBinary` 的启动恢复。
- 调度器绑定的是**安装时的绝对路径**（`install-schedule.mjs:25` 用 `import.meta.url` 解析 `sync.mjs`），
  所以 skill 目录缺失时计划任务会持续失败而不是自愈。
- git 路径还有第二个窗口：先替换 skill、清 backup，再跑 `pnpm install`；依赖安装失败则新 skill 带着旧依赖运行，
  直到下一次升级成功——期间每次同步都会失败（有下一次重试，不丢数据）。
- 建议（P1，2026-11-25 对抗审查细化）：① 启动前恢复的**宿主必须在 skillDir 之外**——调度器入口就是
  `<skillDir>/scripts/sync.mjs`（`install-schedule.mjs:25` + `schedule.mjs:83,156,199`），目录缺失时恢复代码
  自身永远跑不到；候选宿主：configDir 下的 bootstrap 脚本、Go 二进制的 repair 子命令、或把调度器命令改指稳定入口。
  ② 归档路径 `upgrade-archive.mjs` 用 `copy` 直写 skillDir（非 staging+rename），崩在中途留下「存在但残缺」的
  skill，「仅目标缺失才恢复」的判据会把它当健康——归档路径也要改成 staging+rename。
  ③ `movePath` 只对 EXDEV 退化，不重试 EPERM/EBUSY（Windows 占用会直接抛错，而回滚的 rename 也可能被占用，
  从而自造「skill 缺失 + 孤儿 backup」）；补 50/150/400ms 忙重试对齐 `renameatomic.go`。
  ④ 把 `pnpm install` 放在交换**之前**（在 staging 里装好再换）；⑤ 为归档下载与 git/安装子进程补执行超时
  （目前 `spawnSync` 无超时）。
- 数据影响：期间不采集，源文件仍在 → 恢复后按 7 天窗口补回；若停机超过 7 天则落入 G9 的漏洞。

### 2.3 服务端部署（`apps/web/scripts/deploy.mjs`）——已验证

顺序：配置校验 → build → dry-run → 生产路由检查 → 按序 apply migration → 五项 schema 校验 → publish。
窗口：migration 已 apply、新 Worker 未 publish 的几分钟里，**旧 Worker 跑在新 schema 上**，因此迁移必须向后兼容
（expand-contract）。AGENTS.md 已写「迁移不可变」与部署顺序，但**没有通用的 expand-contract 要求**（G4）。
另注：迁移文件不可变不等于数据库没有恢复/补偿手段（D1 时间旅行、备份），v1 的表述过强。

### 2.4 设备重配对与卸载

- 重配对产生新 `device_id`，旧行保留（已知，不重报）。
- 卸载删除配置目录需 `--all` 或 `--remove-config-dir`（`uninstall.mjs:79`）；默认保留状态。
  删除后未上传数据只能从源文件全量重采（受 G9 窗口限制）。

## 三、端到端投递语义与崩溃点（按阶段重写）

`ingestSnapshots` 内部是**多个独立 `db.batch()` 事务**（原始行一批、summary+totals 一批、心跳一批），
不是整个请求一个事务。逐窗口（已验证）：

| 崩溃点                              | 后果                                                                   | 是否丢数据                    |
| ----------------------------------- | ---------------------------------------------------------------------- | ----------------------------- |
| 采集中途退出                        | 部分来源已写 pending；hook 类靠 pending 重试，since 类等下一轮窗口重读 | 窗口内：否；超 7 天：是（G9） |
| 游标写入中被杀                      | temp+rename：要么旧要么新                                              | 否（掉电持久性未测，推断 OK） |
| /check 后、ingest 前                | 未 ack，下轮重查重传                                                   | 否                            |
| 多批上传中某批失败                  | 整次调用返回错误，ack 跳过；已提交批由 hash 幂等吸收                   | 否                            |
| ingest 200 后、ack 前               | 下轮重传，hash 相同被跳过                                              | 否                            |
| **200 但该行未写入（新鲜度拒写）**  | 客户端仍把行标记 Delivered → ack 清 pending                            | **是（G10）**                 |
| 原始行写入后、summary/totals 批失败 | 原始行保留；`/check` 对陈旧 summary 隐瞒 hash → 强制重传修复           | 否（依赖重传）                |
| ack 中退出                          | 每个游标文件独立原子写，跨来源可完成一部分                             | 否                            |
| 已送达但一直未 ack（range 模式）    | Claude/Codex pending 有意保留，可在无 hook 时长期存在                  | 否                            |

**v1 的两处表述错误（已订正）**：
① 「每日自愈全量核对」在当前代码里**不存在**——`backfill.ts:36` 在 `completed_at` 置位后立即返回；
它是 D1 文档中的**计划项（一期 P0）**，不是现状。现状的恢复机制是「重传覆盖 + /check 对陈旧 summary 隐瞒 hash」。
② `invalid`/`before-history-window` 永久确认、`too-far-future` 保留（含 Codex 未来日期退回组确认）——v1 写对了，
`ack_test.go:367,411` 有测试。

幂等基座不变：`snapshot_hash` 相等 → 不写；不等 → 覆盖（含 `costUsd` 漂移，D7 有意设计）。
`synced_at`（=collectedAt）守卫是**另一道闸**：`julianday(synced_at) >= julianday(excluded.synced_at)`
（`upsert.ts:178-181`）——时间回拨时静默拒写且不报错，这就是 G10。

## 五、缺口详解

### 5.1 G1（P1）永久性 400 → 共享 24h 暂停环 + 不可诊断

- 400 在 **/check 与 ingest 两侧都可能发生**，请求内不重试；响应体被排空丢弃；服务端只返回通用
  `Invalid request`（`http.ts:49-51`），没有 index/detail。
- 上传退避状态文件按 **stateDir 共享**（`upload.go:571` 的 `upload-backoff.json`），一个来源的坏行会把同机**全部来源**一起暂停 24h；
  其它来源的成功上传会清计数（缓解暂停），但修不好坏行。
- 持续再发的坏行造成持续失败；since 窗口类来源的坏行还可能随窗口退出转成「静默漏计」。
- **v1 建议里有一条是错的（Codex 证伪）**：二分定位后「像日期越界一样报告+ack」会**永久漏传**——
  400 可能来自旧服务端暂不认识新来源、协议偏斜或时钟超前，修复版本/时钟后该行本可上传，ack 会删掉恢复所需的 pending。
- 修订建议：a) 服务端 400 新增**可选、限量**的 `error.details`（数组下标 + 白名单字段路径 + 稳定 issue code，
  覆盖 `snapshots` 与 `/check` 的 `keys`；原始值不进响应/日志；现有测试精确断言通用错误体，不能改 message）；
  b) 客户端把 details 脱敏写日志；c) 二分**只用于诊断与隔离**（跳过坏行、保留 pending、继续重试其它行），
  永久确认只依赖明确的协议分类（如既有 `invalid`/`before-history-window`）。

### 5.2 G8（P1）skill 目录交换无启动恢复

见 §2.2。建议：skill 交换也走「备份 + 启动前恢复」；`pnpm install` 在 staging 内先行；子进程补超时。

### 5.3 G9（P1）since 窗口类的 7 天重读边界

见 §一。建议（2026-11-25 对抗审查细化）：持久化「最后**已投递**水位」——不能用「sync 退出码 0」判定：
上传暂停时非 hook 运行仍返回 `ExitOK`（`cli.go:282-286`），按退出码推进会让水位在停机期间照常前进，
`since = max(7天, 水位−1)` 永远等于 7 天，A3 要救的场景一行都救不到。必须按**来源**记录（coordinator 逐源
spawn，`coordinator.mjs:340-343`）；自动起点应为 `since = max(今天−30天, min(默认起点, 水位−1天))`——
取「更早的日期」再夹上限；写成「不低于默认」会让 9 天前的水位被 7 天默认顶掉，中断期照旧被跳过
（Codex 终审算例：11-25 恢复，默认起点 11-18、水位−1 = 11-15，取 max 仍从 11-18 开始）。
水位在 `check` 时须不晚于今天（防时钟回拨把 since 推到未来）；损坏/在未来时回退默认并显式告警。
补测试：模拟「上传暂停 9 天」与「单来源失败 9 天」，断言水位不动/其它来源不受影响、恢复后覆盖中断期。
成本澄清：扩展 since 本身不显著增加扫描内存（4.6–7.6 GB 是扫描本身的开销，与窗口无关），
真实成本是快照数约 4 倍带来的 check/ingest 请求增加。

### 5.4 G10（P2）200 但未落库的静默丢更新

- 路径：客户端时钟回拨 → 新量（如 300 tokens）携带较旧 `collectedAt` → `synced_at` 守卫拒写 →
  接口仍 200 → 客户端把该行计入 `Delivered` → ack 清 pending。Codex 内存探针复现（库 165、提交 300、Delivered=1）。
- 建议：服务端按行返回结果（区分**已存同 hash / 过期拒写（`stale-collected-at`）/ Codex 保护 / 已落库**），
  先部署旧客户端可读的响应字段，再改 Go/TS 的行、组、**文件级**确认逻辑——Codex hook 在另有一行可确认时
  会走**整文件确认**（`cli.go:1198-1206`），只把行从集合里剔除并不够；ignored 行**不 ack**，并提示时钟异常。
  与「/check 合并进 ingest 不得复用 skipped 名字」一并设计行级结果契约。

### 5.5 G11（P2）时区变更后的旧日期残留

- 适用条件（Codex 终审收窄）：**采集端时区改变、事件跨日边界、且旧日期键未被新快照覆盖**时成立；仍在同一天的事件写同一键，
  只改 Web 资料时区也不会改客户端配置。Codex 探针在该条件下得到 165+165=330。
- 这是 `(user, device, source, date, model)` 键模型的固有语义。建议：明确「时区变更不重算历史」政策
  （与「不重算历史 costUsd」同款），设置页切换时区时提示；若要纠正，需要「旧时区下该事件的日期集合」，
  当前没有。记录为已知边界，不修。

## 六、已验证健壮的部分（避免重复担忧）

1. 游标/退避原子写（temp+随机后缀+renameatomic；版本状态文件用普通 renameSync，三者实现不同）。
2. 二进制全链（2.1），含回滚与启动前恢复、128 MiB 上下界、重定向约束、无 checksum 拒装。
3. 上传瞬态状态精确为 `408/429/500/502/503/504`（`upload.go:460-468`），不是全部 5xx。
4. 降级守卫；pending 永不回收；`too-far-future` 保留；high-water 由每次扫描写（hook 同样更新扫描 high-water，
   它跳过的是全量扫描之后的 explicit warm 步骤——v1 表述已订正）。
5. 服务端按 hash 幂等；`/check` 对陈旧 summary 隐瞒 hash 强制重传（**这是现状的自愈机制**，每日核对是计划项）。
6. hook 与 scheduled 共用 `collector-run.lock`（`cli.go:209`），采集/上传/确认互斥。
7. migration→publish 窗口与五项 schema gate（deploy.mjs）。
8. Windows 文件占用：50/150/400ms 忙重试（`renameatomic.go`）；持续占用仍会失败，未做真机复验。
9. `0004` 迁移把四元主键换成五元主键后，**旧四元 `ON CONFLICT` SQL 会报错**（Codex 隔离探针）——
   当时的兼容性需要对照当时的 Worker 版本核实；v1「历史迁移遵守了向后兼容」证据不足，已收窄为
   「部署脚本没有自动数据库回滚」。
