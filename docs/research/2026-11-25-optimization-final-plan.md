## 一、业务约束（决定一切取舍）

1. **Web 端时效是硬约束**：用户随时打开都要看到比较及时的数据。任何拉长上传间隔的节流一律不做。
   现状时效构成：hook 冷却 900s + 采集 0–12 分钟（run 中位 4.4 分钟，其中 collect 中位 3.8 分钟占 84%）
   - 上传中位约 6 秒；看板 `no-store` 直读服务端当前已落库数据，公开卡片最多 300s 缓存。
     最坏延迟主因是 scheduled-window 跳过与采集耗时，不是请求节奏。
2. **免费额度必须留余量**：D1 免费 500 万行读/天、10 万行写/天，超限即报错。11-24 实测 474 万行读（94.9%）。
3. **不丢数据**：投递保证按来源分两类（hook 类有持久 pending；其余只有 7 天 since 窗口）。

## 二、最终方案：四个批次

### 批次 A（P1 数据正确性，先做，量小、风险低）

| 项  | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | 验收                                                                                                                                                                                                    |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | 服务端 400 增可选 `error.details`（数组下标 + 白名单字段路径 + 稳定 issue code，覆盖 `snapshots` 与 `/check` 的 `keys`；**不得序列化 Zod 原文**——`invalid_enum_value` 消息含 received 值）；客户端脱敏记日志；二分**只做隔离不做 ack**；上传退避计数**按来源分键**（现状按 stateDir 共享，一个来源的坏行会暂停同机全部来源 24h）；**两个端点都要做行级隔离**：健康行照常交付与确认、坏行保留 pending 单独退避、请求级错误直接报错                                                                                                                                                                                                                          | 路由测试断言 details 形状且不含输入值；`ingest.test.ts:105` 的 `toEqual` 整体断言需同步更新并保留一条「无详情的通用错误」用例；混合好坏行时好行交付、坏行不 ack；退避分键后一个来源的坏行不影响其它来源 |
| A2  | skill 目录交换的启动前恢复——**恢复宿主必须位于 skillDir 之外**（调度器入口是 `<skillDir>/scripts/sync.mjs`，目录缺失时恢复代码自己永远跑不到；候选：configDir 下的 bootstrap 脚本、Go 二进制的 repair 子命令，或把调度器命令改指稳定入口）；归档路径从 copy 直写改为 staging+rename（崩在中途会留下「存在但残缺」的 skill）；`movePath` 补 EPERM/EBUSY 忙重试（对齐 renameatomic 的 50/150/400ms）；`pnpm install` 要在**待启用的完整 workspace** 里跑（只挪到 skill 交换前，仍可能让已原地更新的 checkout 配旧依赖）；归档下载与子进程加超时。**分步发版**：先让存量调度与 hook 入口指向稳定启动器，再启用受锁保护的交换，恢复与手动/计划升级共用同一把锁 | 验收必须**在第一跳之后强制终止**（只注入第二跳 rename 抛错会走原地回滚，不启动恢复也能通过，测不到真缺口）；另覆盖归档复制中断与目标缺失；占用重试有测试                                                |
| A3  | 持久化「最后**已投递**水位」（不是「sync exit 0」——上传暂停时非 hook 运行仍返回 0（`cli.go:282-286`），按退出码推进会让水位在停机期间照常前进、永久失效）；**按来源**记录（coordinator 逐源 spawn）；自动起点 `since = max(今天−30天, min(默认起点, 水位−1天))`——注意是取更早的日期再夹上限，写成「不低于默认」会让 9 天前的水位被 7 天默认顶掉、中断期照样跳过；显式 `since` 仍优先；水位按上传目标/设备/来源维护，只在该来源实际完成覆盖与投递后推进；损坏或在未来时回退默认并显式告警                                                                                                                                                                   | 模拟「上传暂停 9 天」：水位不动，恢复后覆盖中断期；单来源失败 9 天不影响其它来源水位                                                                                                                    |

理由：A1 把「整源卡在 400 死循环且无法诊断」变成「一眼可诊断」；A2/A3 补上「升级/停机本身会丢数据」的两个真实窗口。
三项都不改协议、不依赖 D1 方案，可独立上线。注意 A2 不是「对齐 `recoverOrphanedBinary`」那么简单——二进制恢复有宿主（由 skill 启动），skill 恢复必须先有 skill 之外的入口。

### 批次 D（P3 按需）

- 限流迁 Workers Rate Limiting binding（注意 token 校验读仍存在）；Go 侧定价 Prepare 同轮共享 + 失败短退避（联网路径只有 Claude Code / Codex 两个来源，工具族不传 Endpoint）；发布源检查缓存 6h；公开卡片/排行榜进一步缓存（三期探针后再议）。
- 429/配额类 5xx：`Retry-After` 被截到 5 秒，耗尽后交给调度器再跑最多 5 轮 → 单个持续失败点可达 18 次 HTTP 尝试，且 24h 暂停只累计非瞬态失败兜不住；应保留服务端给出的最早重试时间、调度器在重采前检查，配额类错误单独延后，两类都保留待交付数据。

## 三、明确不做（已论证）

- 拉长 hook 冷却（现 900s）、抑制空 keep-alive 批次、心跳节流、每日一次性上传、事件级上传。
- 客户端本地哈希缓存（非权威，会永久漏传）；删 90 天前原始行。
- 触发器维护聚合；Durable Objects 聚合（额度与 D1 相同）；Queues write-behind（免费 10k ops/天）；
  KV 缓存层（免费写 1k/天）；Worker 内存暂存（驱逐、跨 isolate 不一致）；R2 暂存。
- 提高客户端批到 500（单请求语句数 ~1020，重试与 CPU 风险）；请求压缩（D1 固定成本不变）。
- 服务端强制最低客户端版本（会与 G1 同构地制造死循环）。
- 设备重配对双计、时区变更旧日期残留、无签名发布（记录为已知边界）。

## 四、文档规则补录（P2，一句话级）

写进 `AGENTS.md` 跨端协议不变量：

1. **发布先后**：服务端先宽化，再按已知版本或显式能力启用收紧语义，兼容期继续接受旧请求（与「不做强制最低版本」一致）；可选字段默认兼容的条件是旧端忽略该字段后仍能正确交付；新来源必须先部署服务端接受、再发布发送它的客户端。
2. **cursor 字段演进**：加字段不改 `version`，但必须同时改 **Go `scan.go` 与 TS `session-cursor.ts` 两侧**的重建携带逻辑并覆盖扫描路径往返测试（两边正常扫描都会重建对象、只保留已知字段）；影响投递的字段要验证旧写者扫描后仍能恢复；升 v2 先两端交付双读、继续写 v1，待旧写者退出再切写版本。
3. **迁移 expand-contract**：migration→publish 窗口内旧 Worker 跑新 schema，迁移必须向后兼容；验收方式为迁移后分别运行当前 Worker 与拟回滚版本的关键 SQL，旧版本退出后再收缩 schema；部署脚本没有自动数据库回滚。
