# 客户端 ↔ 服务端交互节流评估（全场景）

日期：2026-11-25（v2，按 Codex 独立评审修订）。范围：TokenBoard 采集端（Go 客户端 + skill 调度层）与
Worker/API 之间的全部交互路径，逐一核对**请求频率、必要性、每请求的服务端成本、架构设计**，并给出节流优化分层。
配套文档：`docs/research/2026-11-25-d1-read-optimization-research.md`（D1 读量归因与 P0/P1 方案）、
`docs/research/2026-11-25-upgrade-robustness-idempotency-audit.md`（升级发版、幂等性与鲁棒性评估）。
本文是评估，不含代码改动。

标注口径：**已验证** = 读代码/跑命令得到；**推断** = 结构外推、未实测；**未覆盖** 会显式标出。
v2 相对 v1 的修正集中在：冷却真实值（900s 而非 300s）、每日请求数口径（success run / collector 调用 / HTTP 请求
三者分离）、check 的 totals 门归属（P0-b 覆盖）、客户端合批对 totals 次数的影响、`skipped` 语义、
scheduled-window 收窄不构成硬保证、批量测试与 shadow 覆盖边界。

## 零、业务前提：时效性是第一约束

用户明确要求：**用户任何时候打开 Web 端，都应看到比较及时的数据；为省额度而拉长上传间隔的节流不可接受。**
这条前提先于一切节流决策，它划定了可采纳项的边界：

1. **时效由「事件驱动 + 15 分钟冷却」保证（已修正）**：`coordinator.mjs` 的 300s 只是模块内通用默认值，
   真实入口 `notify.mjs` 显式传入 `defaultNotifyCooldownMs = 15 * 60_000`（`notify.mjs:36,61`），
   本机配置也是 `notifyCooldownMs: 900000`。即**当前两次成功上传的最短间隔是 15 分钟**。
2. **端到端可见延迟 = 冷却等待 + 采集耗时 + 上传（已验证）**：本机 11-24（UTC）的 36 个成功 run 时长中位数
   **4.38 分钟**、最大 11.92 分钟（`~/.tokenboard/runs` 的 `durationMs`）。采集耗时按来源差异极大：
   claude-code 调用 `timings.collect` 中位 **282s**、最大 690s；codex 中位 **3s**；`upload` 实测中位约 6 秒（49 次，最大 60 秒）。
   所以 run 时长中位由 claude-code 的扫描主导。看板页面 `no-store` 直读 D1、公开卡片最多 300s Worker 缓存。
   所以常态下看板数据的新鲜度上限 ≈ **15 分钟（冷却）+ 0–12 分钟（采集）**。
3. **采纳的节流项必须是「同样及时、更少请求 / 更少扫描」**：合并批次、消除重复读、去冗余请求都满足；
   「攒着晚点发」不满足。
4. **被此前提直接否决的方向**：进一步拉长 hook 冷却；每日一次性上传；把上传暂存在本地或内存里择机落库
   （后者另外还有正确性缺陷，见 D1 文档 §6.4）。
5. **时效的真实威胁排序（已验证）**：
   a) **`scheduled-window` 闸门**——窗口内 hook 同步被跳过、信号排队等下一次触发（11-24 有 69 次被拦），
   若此后无新用量，最长要等到下一个计划时刻（见 4.13）；
   b) **采集耗时与资源压力**——11-24 有 104 次 hook 被 `resource-pressure` 拦下；采集本身中位 4.4 分钟；
   c) 冷却 15 分钟——它主要限制「连续使用期间的更新频率」，空闲时不影响；
   d) 请求批数——对可见延迟影响最小（上传只需 ~10 秒）。
   结论：要提高时效，先改 a/b，而不是压缩请求数。

## 二、频率实测

### 2.1 调度层（本机日志，口径已修正）

三个口径必须分开统计（v1 混用了它们）：

- **coordinator run**：11-24 = 239 次触发 → 36 成功、201 跳过、2 错误（已验证，`~/.tokenboard/runs` 逐文件聚合；
  **按 UTC 日**——按北京时间重算为 226 run / 28 成功 / 40 次调用，两种口径勿混用）。
  跳过构成：resource-pressure 104 / scheduled-window 69 / cooldown 17 / lock-timeout 11。
- **collector 调用**：36 个成功 run 内共 **49 次成功调用**——其中 13 个 run 顺序同步了 2 个来源
  （coordinator 对每个来源各 spawn 一次 `sync.mjs --source <一个源>`，`coordinator.mjs:340-343`）。
- **HTTP 请求**：由 2.2 的公式从每次调用的快照数推出。

11-23 = 26 个成功 run / 35 次成功调用；11-25 截至 12:00 = 6 个成功 run。

### 2.2 每次 collector 调用的请求数（条件公式）

`UploadSnapshots`（`upload.go:151-176`）对「可上传快照」按 **30 条**切块，每块 1 次 `/check`；
有变化的块再各 1 次 ingest；全部无变化时补 1 次空 ingest（keep-alive）。因此：

```text
check 数  = ceil(可上传快照数 / 客户端批大小)
ingest 数 = max(1, 含变化快照的块数)
```

- 本机典型调用 `skipped: 71–73, upserted: 6–12`（约 80 条快照 / 12 条变化）：若变化集中在 1 个旧批 →
  **4 个请求**（3 check + 1 ingest）；若变化分散在 3 个旧批 → **6 个请求**（3 check + 3 ingest）。
  （Codex 用真实 TS uploader 在内存里复现了 4 与 6 两个值。）
- 按 49 次调用/天估算：全部变化集中 → 每调用 4 请求（3 check + 1 ingest）；分散到 3 个旧批 → 6 请求（3 check + 3 ingest）。取等权均值 5 → **≈245 请求/天/客户端**（≈220 是取 4.5 的下界估计，已弃用）。
- issue #29 的 427 次是 **check 请求数**口径（11-24+11-25 合计，11-25 只计约 1 小时），与 check 数比较才成立。

## 三、每个请求的服务端成本（逐项，代码级）

ingest/check 共同的固定前置（已验证）：

| 步骤       | D1 读                                                             | D1 写    | 出处                                      |
| ---------- | ----------------------------------------------------------------- | -------- | ----------------------------------------- |
| IP 限流    | 1 显式 SELECT + UPSERT 自身的冲突行定位                           | 1 UPSERT | `rate-limit.ts:66-140`，`ingest.ts:17-20` |
| token 校验 | 1 SELECT                                                          | 0        | `middleware.ts:68-103`                    |
| token 限流 | 1 显式 SELECT + UPSERT 冲突行定位                                 | 1 UPSERT | 同上                                      |
| **合计**   | **3 次 SQL 调用；计费行数据 `ON CONFLICT` 语义为 4–5 行（推断）** | **2**    |                                           |

在此之上：

- **ingest**：`markIngestSynced` 最多三条 UPDATE（`repository/sync.ts:3-70`；其中 devices/installations 两条各带
  「token 所属用户」子查询，**不是**简单 1 读 1 写）；随后按 **30 行内部批** upsert
  （每行 1 次 PK 读 + 命中则写 + 每索引 1 行写）；含变化行的内部批各触发一次 totals 刷新
  （现状是全聚合核对 `refresh.ts:113-152`；P0-b 后改为差值 UPDATE）。
- **check**：N key 查询（当前形状按 `(user_id, device_id)` 前缀扫该设备**全部日期**再过滤，不止当天；
  issue 实测 655k/427 次 ≈ 1.5k 行/次，P0-a 后 1 行/key）；`filterExistingHashesWithCurrentCaches`
  还会跑 **summary 陈旧核对 + totals 全聚合**（`snapshot-hashes.ts:46-58`）。

**关键结论（v2 修订）**：

1. **限流固定成本按「HTTP 请求数」计价**：每多一个请求多 2 写、3 次 SQL 读，与请求体大小无关。
   降低请求数 = 直接降低固定写量。
2. **totals 刷新次数 ≈ Σ 每个请求内部含变化行的 30 行批数**（`upsert.ts:20,44`；另有例外：某批零变化但其用户 totals 陈旧时，`listUserIdsNeedingTotalRefresh`（`upsert.ts:37-43`）仍会触发一次刷新；backfill 未完成时门控下两者都不写）。所以**客户端合批确实
   减少 totals 次数**：同样 12 条变化分散在 3 个客户端批 → 3 次刷新；合进 1 个 200 条批 → 1 次刷新
   （Codex 内存探针：80 条中 12 条变化分散时 请求 6→2、totals 刷新 3→1）。v1 的「客户端批大小不改变它」是错的。
   但方向不是单向的：**200 条全变化时刷新 7→7 持平；210 条中仅第 200/201 条变化（同一旧批、分属两个新批）时刷新 1→2 反而增加**——
   收益取决于实际变化分布，只能作为预估。它与 P0-b 互补而非互斥：P0-b 把每次刷新从「全聚合」降到「每 key 差值」。
3. **check 的 totals 门属于 P0-b 的覆盖范围**（D1 文档 §四一期的删除清单明确包含 `snapshot-hashes.ts:58`）。
   v1 把它写成「不在 P0-b 覆盖」，与定稿方案矛盾；一期收益里也不应重复计算「3→1」与「门消失」。

## 四、逐项评估

### 4.1 客户端批大小 30→200（采纳，但须先做预算实测）

- 现状：客户端 `snapshotBatchSize = 30`（`upload.go:31`、`upload.ts:14`）；服务端 schema 接受 **500**
  （`schema.ts:4-5`），请求内再按 30 行分块。30 并非 HTTP/绑定参数硬上限（Codex 探针：200/500 接受、501 拒绝）。
- 收益：请求数近似减半（如 80 条：3 check → 1 check）；变化集中时每调用 4→2 请求；totals 刷新次数按 §三结论 2
  合并下降；限流固定写同比例下降。
- **未证实的风险（v2 新增，必须先测）**：服务端 CPU 与语句数随批线性放大——
  仓库内实测新 key ingest 的 SQL 语句数：30 条输入 ≈64 条、200 ≈410 条、500 ≈1020 条，计算式为
  `2N + ceil(N/30) + 3`（N 条 upsert + 每个 30 行内部批一次 summary/totals 刷新 + upsert 之后的 3 条心跳；不计鉴权/限流）。虽然 `runStatementBatches` 仍按 100 分块、单批语义不变，
  但单请求 CPU 与失败面放大 6 倍以上。上线前必须测：Worker CPU/内存上限、30s 客户端超时、
  末批失败后的重试与 cursor 保留、单条非法数据导致整批失败后的恢复。
- 建议值暂定 200（非 500）：在请求数与单请求预算间取中。

### 4.2 `/check` 的必要性（保留，批次合并后为每调用 1 次）

- 三个理由：① 避免重传未变化的行（bandwidth + 服务端写）；② summary/totals 陈旧时返回空集，强制重传触发自愈
  （`snapshot-hashes.ts:46-58`）；③ 给 UI 报 skipped 统计。
- 合批后从 2–3 次/调用降到 1 次/调用，成本可控。不建议完全删除：删除前提是客户端能自行判断「服务端已有什么」，见 4.9。

### 4.3 把 /check 合并进 ingest（二期可选，语义须先定清）

- 形状：客户端只发 ingest；服务端 response 补计数。旧客户端不受影响（响应加字段）。
- 收益：每调用再减 1 请求；check 侧固定成本与合计读消失；未变化行仍走 upsert（每行 1 次 PK 读，与 check 的
  1 次 key 读等价）。
- **语义陷阱（Codex 探针确认）**：现有 `skipped` 的含义是「服务端返回了相同 hash」。而 SQL 语句未改动
  （`statementChanged=false`）还有另外两种来源：`collectedAt` 较旧被 WHERE 守卫拒绝覆盖、Codex 零值保护
  （`upsert.ts:155-177` 的 hash 守卫与 Codex 零值守卫，synced_at 守卫在 178-181）。探针复现：hash 不等、现状 skipped=0、直接 upsert 写 0 行、若按
  statementChanged 计 skipped=1。**不能复用 `skipped` 这个名字**；应单独给 `unchanged`/`ignored` 字段并定义清楚。
  客户端 cursor 确认继续依据「成功交付集合」，与两个计数都无关（现状已如此）。
- 风险：check 的「陈旧 → 强制重传」自愈语义需由 upsert 内部接管——当前对 unchanged 行确实跑 summary 核对
  （`upsert.ts:34-41`，Codex 内存探针复现了修复成功）；但 P0-b 移除在线 totals 核对后，等价性依赖
  「请求开头的 totals 初始化 + 每日自愈 + backfill 门控」全部落实。文档层面必须把这几个前置写进二期验收。
- 判定：**收益中等、风险低但依赖多**，排在 P0-b 上线并观察一周后。

### 4.4 心跳三写（不采纳节流）

- 现状：每次 **ingest** 请求（含空批次）写 `upload_tokens.last_used_at`、`devices.last_synced_at`、
  `device_installations.last_seen_at`（`sync.ts:11-72`）。**check 请求不写心跳**（`service.ts:23` 只在 ingest 里调）。
- 成本（v2 修正）：≈49 次调用/天 ×（1–2 次 ingest）× 3 行 ≈ **150–300 行写/天**（v1 的 430 把 check 也算进去了）。
  仍不足免费写额度（10 万行/天）的 0.3%。
- 为什么不做：收益与额度相比可忽略；同一轮可有多个 ingest，阈值小于 15 分钟并非零收益，但任何显著阈值都会让「最近同步」
  滞后于真实上传（正是时效信号），与大阈值相比不值得。
- 判定：**保持现状**（原 W4 撤回）。

### 4.5 空 keep-alive 批次（保留）

- 现状：全 run 无变化时发 1 次空 ingest（`upload.go:106-113` 与 169-175 的兜底）。
- 成本：≈8 读 + 5 写/次。本机几乎每次调用都有变化，空批次很少触发。
- 判定：保留。客户端「15 分钟内跳过」会让「最后同步时间」失真是与 §零 冲突的，收益又接近零。

### 4.6 运行频率：hook 冷却（现状 15 分钟，不拉长；是否缩短是产品决策）

- 现状（v1 修正）：真实冷却 = **900s**（`notify.mjs:36`），不是 300s。11-24 的 success run 间隔中位数约 15 分钟，
  与冷却一致；还有一条记录剩余冷却 896570ms（Codex 从 run 记录核对）。
- 「若调到 900s 会降到 12–15 次/天」的假设不成立——现状就是 900s，36 次/天已经是在 900s 冷却下的实测值。
- **不拉长**：任何更长的冷却都是直接的体验降级，违背 §零。
- **是否缩短（15 分钟 → 5 分钟）是产品取舍**：会把调用数按比例放大（上限 ~3 倍），并加重扫描内存压力
  （已被 `resource-pressure` 闸门部分吸收）。若用户认为「15 分钟太旧」，这是第一个该谈的旋钮，但必须和
  「采集耗时 4–12 分钟」一起看——即使冷却归零，单次扫描也要几分钟。

### 4.7 定价目录与发布源检查

- 定价：24h TTL + ETag 304（`catalogue.go:35,258-290`），hook 模式永不联网，同一缓存文件。
  **限定条件（v2 修正）**：①「≤1 次/天」只对成功刷新成立——刷新失败不推进缓存时间，同一次 run 里的多个
  provider（Go 侧 claudecode/codex/ccusagetool 三处各自调 `pricing.Prepare`）会**各自重试联网**；
  TS 侧已有进程内共享结果，Go 侧没有。②单次成功刷新可能读多页。③故障联网点只有 Claude Code 与 Codex 两个 provider
  （`ccusagetool` 调 `Prepare` 但不传 Endpoint，联网前就返回），全源 run 每轮最多 2 个失败联网点、各自可能跨多页。
  建议（P3）：Go 侧在同一次进程内共享 Prepare 结果，失败加短退避。正常路径不再优化。
- 发布源：每个 `--scheduled` run 都 `release.Resolve`，无缓存；4 次/天，不受 D1 计费影响。可选缓存 6h。P3。

### 4.8 重试与退避层次（基本合理，但「无重试风暴」要加条件）

已存在：HTTP 层最多 3 次尝试（250ms→5s 退避，`upload.go:339-383,477`）→ 单 run 内不重复
→ upload backoff（连续 5 次非瞬态 → 暂停 24h）→ coordinator failure-backoff（10 分钟）→ 计划任务整轮重试
（`scheduled-retry.mjs:26`，最多 5 轮）。

**两个放大点（v2 新增）**：① `Retry-After` 被截到 5 秒——服务端 429 若要求等 60 秒，后两次尝试仍落在同一窗口，
3 次立刻用完；② 计划任务失败后最多 5 轮整轮重试，每轮都可能重新采集+上传。二者叠加时限流类失败的成本
是「3 次 HTTP × 5 轮 × 每轮采集」。
建议（P3）：429 按服务端 Retry-After 延后**整轮**（而不是在请求内重试），减少重复采集。
结论改为：**没有在稳态下的重试风暴；限流/超时叠加时存在有界的放大**——单个持续失败点可达 18 次 HTTP 尝试（3 次/轮 × 6 轮），24h 暂停只累计**非瞬态**失败，兜不住 429/5xx 这条分支；真正兜底的是保留服务端最早重试时间并在重采前检查（归入批次 D）。

### 4.9 客户端本地哈希缓存（否决）

- 想法：客户端记住上次交付的 (key, hash)，本地比对后只传差异，彻底去掉 /check。
- 否决理由：本地缓存**非权威**——服务端回滚、设备重配对（device_id 变）、`invalid` 行永久丢弃、服务端
  correction 等场景会让「以为已交付」变成永久漏传。为省 1 次请求/调用引入静默丢数据风险不值得。
  （Codex 复核：提高批大小不破坏 hash 幂等或 ack——ack 在整个上传成功之后，源码未见相关约束。）

### 4.10 服务端内部 30 行批（交给 P0-b，不单独动）

- `snapshotUpsertBatchSize = 30`（`upsert.ts:16`），每个含变化行的内部批跑一次 totals 全聚合。
- 提高到 100 不可行地简单：100 个 summary 刷新 + 1 条 totals = 101 条，`d1MaxBatchStatements=100`
  （`types.ts:14-15`）会再次分块，「一次刷新」不成立。P0-b 落地后该问题自动消失，**不单独做**。

### 4.11 限流写（交叉三期）

- 每请求 2 写、3 次 SQL 读。迁移到 Workers Rate Limiting binding 可省掉，但**上传 token 的数据库校验读
  （1 次 SELECT）仍在**，迁移不能把固定读降到 0。60s 窗口可表达现有策略；近似语义需接受。
  交互侧影响：请求数越少收益越小——先做 4.1 再评估。

### 4.12 架构替代：事件级上传 / 每日一次性上传（均否决）

- **现状**：客户端把 usage 在本地聚合成 `(source, usageDate, model)` 快照上传，服务端按五元键幂等 upsert。
- **替代 A（event-sourced）**：逐会话上传——传输行数放大一个数量级、服务端要聚合、会话指纹进传输面
  （隐私面扩大）、游标/幂等/session-only 契约全套重写，对 D1 行读只会更糟。**否决**。
- **替代 B（每日一次）**：当天数据最多滞后 24 小时，直接违背 §零。**否决**。

### 4.13 闸门对时效的隐性税：scheduled-window（问题成立，v1 的建议不充分）

- 机制：`notify.mjs:50` `defaultScheduleWindowMs = 30 * 60_000`，对称地覆盖计划时刻前后 30 分钟
  （`schedule.mjs:239`）；窗口内 hook 触发一律跳过并保留信号（`coordinator.mjs:153-161`），由**下一次触发**
  补做。计划任务本身不经过 coordinator；**它也不写 `last-success.json`**（该文件只由
  `coordinator.mjs` 的 `writeSuccessfulSyncCheckpoint` 写），所以「计划同步后由冷却吸收重复扫描」这个说法
  不成立——冷却根本没被计划同步推进。
- 代价（已验证）：默认 4 个计划时刻 × 前后 30 分钟 = 每天最多 4 小时 hook 同步被压住；11-24 有 69 次被拦。
- 时效后果：用量在窗口内结束、之后无新触发时，最长要等到下一个计划时刻（例如 12:05 结束 → 18:00 才同步）。
- **v1 建议（非对称窗口）不充分（Codex 探针确认）**：哪怕窗口缩到 ±5 分钟，12:02 的触发仍会被跳过、
  `trailingScheduled=false`，下一次仍可能到 18:00。**根因不是窗口宽度，而是「被跳过的信号没有带截止时间的续跑」**。
- 建议（v2）：保留窗口去重，但让窗口内被跳过的信号**排一次 trailing 续跑**（复用现有
  `scheduleTrailingSources`/`trailingDelayMs` 机制），延迟 = 距最近的计划时刻 + 采集余量，且只排一次；
  这样「计划同步覆盖它」成为硬事实而不是假设。可选再收窄窗口后沿（前 30/后 10 分钟）。
- 代价：窗口内每次触发会多一次「定时续跑」判定，成功同步次数在覆盖区间内基本不变（续跑只在计划同步
  **没**接住信号时才真正多跑一次）。

### 4.14 同一 run 内的跨来源合批（新候选，P2）

- 事实：11-24 的 36 个成功 run 里有 13 个顺序同步两个来源，每个来源各 spawn 一次 `sync.mjs --source <一源>`，
  各自支付 check、ingest、鉴权限流的固定成本（`coordinator.mjs:340-343`）。
- 候选：hook 侧走 `--source all`（只采集 Claude Code/Codex 后统一上传），把两个来源的快照合进同一批请求。
  收益：多来源 run 的固定成本减半。代价：单来源失败时的交付与 cursor 边界要重新验证——
  现有 ack 语义是按来源分别确认的（session 文件源仅 hook 模式确认），合批后必须证明「一个来源失败不影响另一个」。
- 判定：**值得评估但不入一期**——与 4.1 的收益部分重叠，先把 4.1 的预算与语义测清楚。

## 五、推荐组合

在 §零 的前提下，采纳项全部是「消除冗余请求」，不改变交付时点：

| 期                    | 改动                                                                    | 交互侧收益                                          | 时效影响     | 依赖         |
| --------------------- | ----------------------------------------------------------------------- | --------------------------------------------------- | ------------ | ------------ |
| 一期（与 D1 P0 同批） | 客户端批 30→200（Go + TS 同步改）+ 服务端预算实测                       | 请求数 ≈减半；totals 刷新次数随合批下降；固定写减半 | 无（更快）   | 预算实测通过 |
| 一期（时效）          | scheduled-window 被跳过的信号排一次带截止的 trailing 续跑（4.13）       | 无（请求量基本不变）                                | **显著改善** | 无           |
| 二期                  | ingest response 补独立计数字段，客户端可选停用 /check                   | 每调用请求 2→1；固定成本再减                        | 无           | 一期 + P0-b  |
| 三期（按需）          | Go 侧定价共享 + 失败短退避；429 延后整轮；发布源缓存 6h；限流迁 binding | 少量固定/故障请求                                   | 无           | 用户拍板     |
| 待评估（P2）          | hook 侧跨来源合批（4.14）                                               | 多来源 run 固定成本减半                             | 无           | ack 边界验证 |
| 产品决策              | 冷却 900s 是否缩短（4.6）；窗口是否再收窄后沿                           | 冷却缩短会放大请求量                                | 直接影响     | 用户拍板     |

明确**不列入**：心跳节流（4.4，撤回）、抑制空批次（4.5）、拉长冷却（4.6，否决）、每日一次性上传（4.12）。

量化（口径：49 次调用/天、平均 5 请求/调用 ≈ 245 请求/天/客户端；每调用 3 check + 1–3 ingest）：

- 一期合批：≈245 → ≈123 请求/天；限流固定写 490 → 246；totals 刷新次数视分布再降。
- 二期：≈123 → ≈50 请求/天（每调用 1 次 ingest）。
- 所有这些都**不改变上传时点**；4.13 的 trailing 续跑才是真正缩短「最坏可见延迟」的改动。

## 六、明确不做

- 客户端本地哈希缓存（4.9）。
- 心跳三写节流（4.4）、抑制空 keep-alive 批次（4.5）、拉长 hook 冷却（4.6）。
- 提高客户端批到 500（单请求语句数 ~1020，重试与 CPU 风险过大）。
- 把 pricing 全量同步进客户端。
- 用 WebSocket / 长连接（无实时下推需求）。
- 请求压缩：现有 ~24KB 级批量下收益仅是传输字节，D1 固定成本不变，服务端还需支持解压与解压后限长。记录，不做。

## 七、验证口径

1. 客户端批大小：**shadow/parity 不覆盖上传分批**（它比较的是采集输出；两端批大小不同也能得到相同 snapshot）。
   必须直接对照两端相同输入的请求序列：更新 `clients/go/internal/upload/upload_test.go` 与
   `packages/collector/src/upload-batches.test.ts`，断言 200 条输入的 check/ingest 次数。
2. 服务端预算：200 条全部变化 / 全部命中 / 混合变化三种输入，测 Worker CPU 与内存、语句数、
   末批失败与重试后的一致性（隔离 Worker，非生产）。
3. 请求数：本机连续两次同步，抓包或 `wrangler tail` 计数；同时确认 run 总耗时不升。
4. 线上：`wrangler d1 insights --sort-by=reads` 前后对比，按 D1 文档 §八 分层验收。
5. 不在 chaosyn 生产做任何写操作验证；只读指标走 issue #29 的 GraphQL。
